# 全面思考

在分析、重构、或提议任何方案之前，必须构建完整且精确的图景。两条硬标准：

- **全面**：涉及一个东西时，把它**所有**的关联方都列出来，不止眼前那一个。
- **精确**：每个断言都要有 `file:line` 代码依据；在验证前不得从印象/记忆下结论。

## 核心流程

### 1. 动手前：穷举关联面

对任何要分析/改动的模块，先回答：

- **它被谁读？** 搜所有读取它的字段/函数的调用点（grep 字段名，不止模块名）。
- **它写谁？** 列出它写入的所有文件/注册表/状态。
- **改一处要连带哪些？** 把耦合点全部列出，缺一个就是"修一次坏一次"的来源。

例：本项目一个"模型"散落在 5 个注册表（character.json / live2d_models.json / avatar_profiles / avatar.yaml / 模型目录），只改一个必出问题。

### 2. 验证优先：代码是事实

- 用 Grep/Read 验证，不以文档（ARCHITECTURE.md/README/注释）为事实。
- **先判死/活**：一条代码路径是"活的"（当前被触发）还是"休眠/遗留"（接线了但没触发）？调用链要追到触发点（`grep` 谁调用了它），不能只看函数存在。
  - 例：`_sync_gsvi_models` 存在≠活跃，要确认有没有 `.char` 文件触发。
- 每次断言前问：这句有没有 file:line？没有就先去查。

### 3. 建议方案时：给出精确的改动面

- 每处改动列清：改哪个文件、哪几行、为什么。
- 区分"复用已有"（无需动）vs"需要改"vs"是遗留可清理"。
- 明确哪些是**硬失败**（缺失即炸）、哪些是**软降级**（缺失只变呆/变空）。
- 诚实给出代价：这个方案引入了什么新复杂度、赌了什么假设。

### 4. 收尾：交叉引用检查

- 删除/移动任何文件或字段前，先扫全仓库引用（含测试、前端、Electron、.env、文档）。
- 方案落地后：跑相关测试 + 验证真实运行路径（不是只"编译通过"）。

## 反面清单（本会话踩过的坑）

- 凭印象说"模型已系统级共享"——只对了一半，没验证"添加"这个操作是否也存在。
- 说"声线三份副本"——没确认复制路径是活的还是休眠的。
- 提议重构时忽略已有的并行系统（catalog.py vs loader.py 两个导入系统）。
- 把"引用复用"和"单一事实来源"混为一谈。
